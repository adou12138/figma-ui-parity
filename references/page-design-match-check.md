# 页面 ↔ 设计稿对应性预检（步骤 3.5）

## 目的

防止**"比错对象"**：设计稿画的是 A 页面，却拿 B 页面来对比，导致报告里全是伪问题。

本 skill 的逐项核对是**机械的结构 / token 级比对**——它不会自己判断"对象对不对"，哪怕页面与设计稿完全无关，也照样产出通过/不通过清单。因此必须由步骤 3.5 **显式把关**，不能依赖逐项核对自己去发现问题。

## 执行时机

**登录成功（步骤 3.2）之后、步骤 4 提取元素之前。** 需要登录是因为未登录时读到的 title/结构是登录页，取不到目标页真实指纹。

## 一、先枚举页面级 Frame，再取"设计稿指纹"

不能把 URL 的 `node-id` 默认当作完整页面。先读取该节点的 `type`、`name`、尺寸和父级关系：

- `DOCUMENT` / `CANVAS`：继续枚举其子节点；
- 页面级 `FRAME`：可作为候选设计页；
- `COMPONENT`、`INSTANCE`、子 `FRAME` 或明显小于页面的节点：只能作为组件/局部参考，不得单独生成页面级报告。

当文件包含多个页面 Frame 时，先做浅层文件读取，列出每个顶层 Frame 的 `nodeId`、名称、宽高和首层区块；再按名称、URL 路径和页面指纹映射到页面。建议映射规则：

| 设计 Frame | URL 路径 | 页面性质 |
|---|---|---|
| 通讯录 | `addressbook.aspx` | 成员列表主页 |
| 管理员·管理 | `qywxusermanage.aspx` | 管理员列表 |
| 成员·作答 | `contactsanswer.aspx` | 成员作答配置 |
| 其他设置 | `addressbooksetting.aspx` | 通讯录设置 |

若完整文件响应过大，必须使用“浅层枚举 → 按 Frame 分片读取”；禁止回退到某个小子节点并报告“设计稿不足”。只有名称、路径和页面指纹无法唯一对应时，才请求用户选择。

从选定的页面级 Frame 数据中提取：

| 指纹项 | 怎么取 |
|---|---|
| 页面主题 | Figma 文件名（如 `【1036854】通讯录：布局及细节优化`） |
| 顶层结构 | 顶层 frame 名与尺寸（如 `FRAME 1449×786`） |
| 功能区块 | 主要区块 / Section 名 |
| 关键字段 | 表单字段名、列表表头、弹窗标题（如 `用户ID*` `姓名*` `新建文件夹`） |
| 页面性质 | 由上述推断：是**列表主页** / **设置页** / **详情弹窗** / **表单页** |

## 二、取"页面指纹"

用 `browser_evaluate` 在真实页面上取：

```javascript
({
  title: document.title,
  path: location.pathname,
  nav: Array.from(document.querySelectorAll('nav a, .nav a, .menu a, .sidebar a'))
        .map(a => a.innerText.trim()).filter(Boolean).slice(0, 12),
  heads: Array.from(document.querySelectorAll('th')).map(t => t.innerText.trim()).slice(0, 12),
  labels: Array.from(document.querySelectorAll('label')).map(l => l.innerText.trim()).slice(0, 12),
  body: (document.body.innerText || '').replace(/\s+/g, ' ').slice(0, 500),
})
```

## 三、判定矩阵

| 判定 | 判据 | 处置 |
|---|---|---|
| **匹配** | 页面 title/URL 主题、顶层导航、主区块、表头/字段与设计稿主题**同源** | 正常进入步骤 4 |
| **存疑** | 部分对上、部分对不上（如同域但功能不同，或设计稿含多帧无法定位主帧） | 继续跑，但**报告顶部显著标注**："页面与设计稿对应性存疑，结论仅供参考" |
| **很可能不匹配** | 页面性质与设计稿**明显不同**（如设计是列表主页、页面是设置页；或 title 主题与设计稿文件名无交集） | **用 `AskUserQuestion` 停下来问用户确认**：`["确认就是比这个，继续", "我换一个页面链接", "我换一份设计稿"]`。**不要默默跑完出报告** |

### 判定技巧

- **title vs 设计稿文件名**是最快的信号：两者主题词应有交集（如设计"通讯录" ↔ 页面 title"通讯录"）。
- **URL 路径**是强信号：`addressbook.aspx`（主页）与 `addressbooksetting.aspx`（设置页）是**不同页面**；`...Setting.aspx` / `...Config.aspx` 后缀通常表示设置/配置页，不是业务主页。
- **表头/字段**是决定性信号：设计稿的关键字段名（如"用户ID/姓名/部门"）应在页面表头或 label 中出现。
- 设计稿含**多个顶层 frame** 时，先与设计稿确认哪个是主帧；若用户未指定 nodeId 且存在歧义，按"存疑"处理并在报告中列出各帧。

## 四、真实案例（本 skill 已踩过的坑）

设计稿 `【1036854】通讯录：布局及细节优化`：

- 画面内容为**成员列表 + 新建文件夹弹窗 + 用户ID/姓名/出生日期/手机/邮箱字段** → 这是**通讯录主页**的性质；
- ✅ 对应页面：`addressbook.aspx`（title `通讯录`，含"系统设置/通讯录/成员分析…"导航与"用户ID/姓名/部门/创建时间/操作"表头）→ **匹配**；
- ❌ 不对应：`addressbooksetting.aspx`（通讯录**设置**页）→ **很可能不匹配**。

曾经在未做本预检的情况下，拿 `addressbooksetting.aspx` 跑完整个流程且全程未提示，报告里出现的"主色按钮缺失""Section 分区缺失"等结论，**实为页面错配导致的噪音**，会误导修复。这就是步骤 3.5 存在的直接原因。

## 五、与流程其他步骤的关系

- 本步骤**不替代**逐项核对，只是在其之前加一道"对象正确性"闸门；
- 判定"存疑/不匹配"被用户确认继续后，仍照常执行步骤 4-7，但需在报告 meta 中记录 `correspondence: "suspect" | "mismatch_confirmed"`，便于回溯；
- 若用户换链接或换设计稿，回到步骤 1 / 步骤 2 重新取数，不要复用已提取的旧数据。
